## 3. 새 폴더에서 받는 절차

기준 재현에서는 GitHub의 `codex/stage21-runbook`을 새 빈 폴더에 복제한 뒤 기준 커밋으로 detached checkout했다. `.env`, 호스트 개인 설정, 인증 보관함, DB를 원래 폴더에서 복사하지 않았다.

다른 사람이 **최종 제출 커밋**을 받으려면, 새 PowerShell에서 아래를 실행한다. `keshev-repro`가 이미 있으면 덮어쓰지 말고 새 폴더명을 고른다. 첫 줄의 저장소 상위 폴더는 본인의 실제 작업 위치다.

```powershell
git clone --branch codex/stage22-reproduction --single-branch https://github.com/ejdehdtjr-afk/choi-bujang-secret-vault-2.git keshev-repro
Set-Location .\keshev-repro
git checkout --detach <제출란의-실제-40자리-커밋>
git rev-parse HEAD
git status --short
```

`<제출란의-실제-40자리-커밋>`은 실행 전 실제 해시로 교체한다. 브랜치 이름만 보고 다른 커밋의 검사를 섞지 않는다. `git status --short`가 비어 있는지 확인한다. 이어 [21단계 실행 설명서](STUDENT_RUNBOOK.md)의 환경·명령·기본/예제 구분을 따른다. 그 문서의 절대경로는 원래 PC의 예시이므로 새 복제본의 실제 경로로 바꾼다. 앱 코드는 그 절대경로에 의존하지 않는다.

```powershell
Set-Location .\on-client
node --version
npm.cmd --version
git --version
npm.cmd run check
npm.cmd run demo
```

기본 브라우저 주소는 `http://127.0.0.1:5189/`이며, 포트가 사용 중이면 기존 앱을 종료하지 말고 이번 창의 `ON_PORT`만 사용하지 않는 번호로 바꾼다. 예제의 시작 신호는 `케셰브 예제: ...`다. 서버를 실행한 창에서 Ctrl+C로 종료하고 같은 명령으로 다시 켠다. `npm.cmd start`의 기본 미연결을 실제 연결 성공으로 기록하지 않는다.

**브라우저 확인은 아직 미확인이다.** 내장 브라우저 접근이 보안 정책으로 차단됐던 상태이므로 우회 자동화로 대체하지 않았다. 사람이 새 복제본의 주소를 열어 보호 현황·업무 앱·보안 기록, 필터·상세와 포커스 이동을 확인해야 한다. HTTP 200과 모의 DOM 결과를 실제 브라우저 시연으로 표현하지 않는다.

## 4. 자동 재현 도구의 실행·증거

Git 최상위에서 실행한다. 출력 폴더는 **저장소 밖에 미리 만들어 두고**, 기존 파일이 아닌 새 이름을 사용한다. 아래 `C:\제출증거`는 설명용 예시이며 본인의 실제 폴더로 바꾼다.

```powershell
node .\on-client\tools\student-reproduce-check.mjs --output 'C:\제출증거\keshev-final-evidence.json'
```

도구는 기본값으로 자신의 파일 위치에서 Git 루트를 찾는다. 다른 깨끗한 복제본을 검사할 때만 `--project` 절대경로를 줄 수 있다. 기존 증거는 덮어쓰지 않는다. `git status`가 깨끗하지 않으면 커밋 결속을 위해 검사를 중단한다.

검사 동작:

1. 현재 저장소·40자리 HEAD·시작/종료 시각·Node/npm/Git/PowerShell 버전을 기록한다. Windows PowerShell 5.1의 새 프로세스에서 `npm.cmd run check`를 실행한다. 신규 프로그램 설치는 하지 않는다.
2. 현재 커밋에서 읽은 학생 함수에 모의 입력을 전달한다. 이 구간의 `fetch`는 실패하도록 막고, 클립보드도 가짜 저장소를 사용한다. 실제 계정·실제 클립보드 성공으로 기록하지 않는다.
3. **5216 포트**에서 예제 → 종료 → 기본 미연결 → 종료 → 예제 재시작을 실행한다. Node로 `src/server.mjs`를 실행하며 이는 package 스크립트의 동일 진입점이다. 인증 관련 부모 환경은 넘기지 않는다. `ON_PROJECT_DIRECTORY`를 전달하지 않고 승인 패키지를 빈 배열로 고정해 외부 OSV 조회를 열지 않는다.
4. `/`, `/student/extension.mjs`, `/api/me`, `/api/events`(예제), `/api/diagnostics`, `/api/vulnerabilities`의 로컬 응답만 확인한다. AI·접근 판정·조치 POST는 호출하지 않는다.
5. 자기가 띄운 자식 프로세스만 종료하고 포트 응답이 멈췄는지 검사한다. 5216이 이미 사용 중이면 그 프로세스를 종료하지 않고 검사 실패로 남긴다. 자식 서버의 시작 문구를 확인하기 전에는 기존 포트의 응답을 자기 결과로 채택하지 않는다.

코드 해시는 Windows 줄바꿈 차이를 제외하기 위해 UTF-8 LF 정규화 후 SHA-256(`hashFormat: sha256-utf8-LF`)이다. 현재 실행한 검사 도구의 해시도 `runnerSha256`에 남긴다. 기준/최종 증거의 런타임 코드 해시와 검사 도구 해시를 대조하며, 다르면 같은 코드의 결과로 합치지 않는다.

출력 JSON의 `kind`는 `actual-command`, `actual-local-HTTP`, `mock-DOM`, `source-inspection`으로 구분된다. `productionVerified:false`는 실제 시스템 인증을 하지 않았다는 뜻이다. Windows 외 환경, Node 기준 24.19.0, 브라우저는 별도 확인 대상이다.

처음 제한 실행 계정에서는 복제본 소유권 차이로 Git 읽기가 거절됐다. `safe.directory`나 전역 정책을 바꾸지 않고 실제 사용자 권한으로 다시 실행했다. 이는 격리 실행 환경 차이이며 앱 코드를 수정해 숨기지 않았다. 앞선 v1/v2 외부 증거 파일은 보존하고, 위 표에는 최종 도구 해시가 기록된 v3 기준 기록만 사용했다.

## 6. 최종 커밋의 별도 실행 기록

이번 문서·기준 증거·검사 도구를 커밋해 GitHub에 올린 **뒤**, 또 다른 새 폴더 `stage22-final-20261103`에 최종 브랜치를 복제하고 명시적인 40자리 커밋으로 checkout한다. 그 안의 `on-client/tools/student-reproduce-check.mjs`로 다시 검사한다. 원래 폴더나 기준 복제본의 `.env`·보관함·DB는 복사하지 않는다.

최종 결과 파일은 프로젝트 밖의 `output/stage22-final-evidence.json`으로 보존하고, 작업 보고에서 그 파일과 실제 최종 커밋 해시를 함께 전달한다. 이 파일은 검사 대상 커밋을 바꾸지 않기 위해 Git에 뒤늦게 추가하지 않는다. 문서 초안 시점에는 이 **최종 커밋 실행**을 아직 수행하지 않았으므로 완료로 기입하지 않는다.

최종 보고를 읽는 사람은 다음을 확인한다.

- `commit`이 제출란의 40자리와 정확히 같은가? 새 복제본에서 실행했는가?
- `runnerSha256`와 `codeHashes`가 이 커밋의 실제 파일과 같은가? `gitStatusBefore/After`가 깨끗한가?
- 각 체크의 `result`, `kind`, `checkedAt`을 구분했는가? 브라우저·운영 연결 미확인이 남아 있는가?
- `succeeded`의 모의 관측을 실제 학생 조치 성공으로 서술하지 않았는가?

코드 문제가 발견되면 수정 후 새 커밋을 만들고 **그 새 최종 커밋 전체를 다시 재현**해야 한다. 이전 커밋의 성공 기록을 새 버전의 성공으로 붙이지 않는다. 문서만 바뀌어도 최종 40자리 해시와 실행 보고의 결속은 다시 확인한다.

|---|---|---|
| 원래 소스·Git 기록 | 원래 작업 폴더 유지, 원격 브랜치와 40자리 커밋 기록, 공식 원문 JSON을 저장소 밖에 보존 | 새 빈 폴더에 해당 커밋을 clone/checkout. 원래 폴더에 `reset --hard`·강제 덮어쓰기 하지 않음 |
| 미커밋 학생 작업·로컬 메모 | 작업 전 `git status`로 별도 변경 확인. 비밀 없는 파일만 개인 보존 위치에 별도 사본 | 이번 작업 시작 시 기존 변경은 없었음. 다른 작업을 스테이징·삭제하지 않음 |
| 개인 계정·인증 보관함·설정 | 제공 호스트의 프로젝트 밖 보관함과 제외 설정은 원래 위치에 유지. Git·원문 묶음·공개 문서에 넣지 않음 | 새 복제본은 기존 자격의 무작정 복사 없이 공식 계정·앱 승인 절차를 다시 따른다. 이 승인·이관 자체는 미실행 |
| 실제 학생 DB·감사·조치 상태 | 이번 검증은 실제 DB를 연결·수정하지 않음. 백업이 필요하면 담당자가 쓰기를 멈추는 절차와 일관된 스냅샷·암호화 보관을 준비 | 새 시험 위치에서 무결성·소유자·현재 원천 결과를 먼저 확인. 실운영 복원은 미실행이며 문서만으로 성공을 주장하지 않음 |
| 이미 전달된 보안 조치 | requestId·receiptId·대상·세대와 원천 관측을 보존 | 코드 되돌리기·화면 취소·DB 과거 사본 복원이 실제 조치 효과를 취소하는 것은 아님. 자동 재집행하지 않음 |
| 재현·제출 증거 | 기준 JSON은 이 커밋에 포함, 최종 실행 JSON과 공식 원문 JSON은 저장소 밖에 각각 새 파일로 보존 | 이전 파일을 덮어쓰지 않고 커밋·해시·시각으로 구분. 백업 복원 자체의 실측은 미확인 |

원문 JSON은 소스 전달용이며 실제 사용자 데이터·인증 보관함의 백업이 아니다. 이전 공개 Git 기록의 비밀 부재나 삭제 완료를 이 문서로 인증하지 않는다. 문제가 의심되면 담당자에게 알리고 공식 교체·복구 절차를 따른다.

## 8. 22단계 제출

최종 커밋을 정한 뒤 공식 `student-source-cli.mjs`를 **Git 최상위**에서 실행한다. 도구·출력 위치는 저장소 밖이어야 하고, 출력 폴더를 먼저 준비하며 기존 파일을 덮어쓰지 않는다. `--commit`에는 작업 보고에서 확인한 최종 40자리 값을 명시한다. 도구는 커밋된 원문만 묶고 학생 코드 실행·업로드·제출은 하지 않는다.

21·22단계는 과제 화면에 저장소 주소와 커밋을 직접 입력한다. Workbench의 13~20단계용 제출 준비와 혼동하지 않는다. 같은 단계의 `비공개 저장소 원문 묶음`에 생성 JSON을 선택하고 사용자가 제출한다. 원문 전달만 실패하면 기존 접수를 유지하고 `원문만 다시 보내기`를 사용한다. 비공개 저장소를 공개로 변경할 필요가 없다.

이번 작업은 **검증 중 버전의 재현·문서화**다. 서버 AI의 원문 검토, 이 도구의 모의 검사, 로컬 실제 실행, 사용자의 브라우저 시연, 실제 운영 인증은 서로 다른 증거다. 공식 판정이나 전체 기능·운영 안전을 만들어 내지 않는다.
